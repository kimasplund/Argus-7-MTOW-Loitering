# ARGUS-7 — CAD Rebuild, Simulation Stack & Design Optimisation

**Date:** 2026-08-20 · **Status:** Design approved, spec under review · **Supersedes:** nothing (first engineering-code spec for this repo)

## 1. Problem

The repo holds a verified v1.0 paper design (`docs/argus7_design_report.md`) but **no code**. Every number in it was produced by analysis that did not survive the originating session, so nothing is reproducible, and the one machine-readable artifact — `model/argus7_model.scad` — is defective in three independent ways:

| # | Defect | Evidence |
|---|---|---|
| 1 | **Wing and fuselage share an axis.** `halfwing()` spans along `y` and is mirrored in `y`; the fuselage pod also runs along `y` (`-0.4` → `-fuse_l`). Booms run along `y` but are *spaced* in `x`. The wing is rotated 90° relative to the airframe. | `model/argus7_model.scad:9-15,27-31,40` |
| 2 | **Geometry is the superseded Gemini set.** `c_root=0.674`, `c_tip=0.303` imply S=4.525 m² (+16% vs 3.9) and AR=19.0 (−13.8% vs 22). Report §10 records `0.674 → 0.581` as an already-corrected error. Header comment claims MAC 0.421; its own numbers give 0.512; the report says 0.441. Three values, none agreeing. | `model/argus7_model.scad:2-5` vs report §2, §10 |
| 3 | **No airfoil.** The wing is two scaled spheres in a `hull()`. No section, no twist (design pack specifies Prandtl bell spanload), no dihedral, no sweep. Unmeshable, unanalysable. | `model/argus7_model.scad:9-15` |

Defect 2 is the important one: it is a *known-corrected* error that leaked back into the only machine-readable artifact. That is a data-integrity failure, not a modelling slip, and the fix must be structural — not a one-off correction.

## 2. Goals

1. **Reproducibility.** Every headline number in the report is regenerated by committed code from a single parameter file.
2. **A correct, analysable CAD model.** Real airfoil lofts, correct axes, watertight solids, CFD-meshable.
3. **An answer to "is 250 kg / AR 22 actually right?"** — by freeing the whole design point and optimising it.
4. **Independent validation** of each layer against external data, culminating in reproducing a real aircraft's measured record.

## 3. Non-goals

- No hardware, procurement, or build.
- No CFD inside the optimisation loop (Section 7 explains why).
- No regulatory submission work; §9 of the report stays headline-level.
- Not re-litigating v1.0's *mission requirements* — payload 50 kg / 500 W and the loiter mission are fixed inputs.

## 4. Architecture

Layered, with a torch core. Classical solvers are **validators that feed coefficient databases**, not inner-loop evaluators.

```
design/argus7.yaml ──► geometry.py (closure asserts) ──┬──► cad/       (build123d → STEP/STL/SCAD)
                                                        ├──► aero/      (XFOIL, NeuralFoil, AVL, buildup, SU2)
                                                        ├──► prop/      (BEMT, engine+BSFC map)
                                                        ├──► struct/    (analytic spar, CalculiX FE)
                                                        └──► mission/   (batched differentiable torch sim)
                                                                   │
                                                            opt/ (Sobol → autograd → CMA-ES/NSGA-II)
                                                                   │
                                                            verify/ + gauntlet ──► report v2.0
```

**Why torch core (chosen over monolithic AeroSandbox):** writing the mission integration in torch makes it simultaneously *batched* (10⁶–10⁷ designs per GPU pass) and *differentiable* (gradients through the whole fuel-burn integration). AeroSandbox's CasADi/IPOPT optimiser is CPU-only and would leave the GPU idle. AeroSandbox is retained as an **independent cross-check oracle** in `verify/`, which is more valuable than using it as the backbone.

**Why not RANS-in-the-loop:** each RANS evaluation is hours. CFD instead validates the drag buildup at 3–6 points and supplies a surrogate correction factor to C_D0.

## 5. Data contract — the structural fix for Defect 2

One file, `design/argus7.yaml`, is the sole source of truth. Every module reads it; **no module hardcodes geometry.**

`design/geometry.py` derives all dependent quantities and asserts closure:

```
b     = sqrt(AR * S)
c_root = S / ((b/2) * (1 + taper))
c_tip  = taper * c_root
MAC    = (2/3) * c_root * (1 + taper + taper^2) / (1 + taper)
assert |S - (b/2)*(c_root + c_tip)| < 1e-9
assert |AR - b^2/S|                 < 1e-9
```

These assertions run in `pytest` and in CI. A future edit that reintroduces an inconsistent chord **fails the build**. Header comments in generated files are emitted by code, never hand-written — the "three conflicting MAC values" failure mode becomes unrepresentable.

Two committed design points:
- `design/argus7_v1.yaml` — the report v1.0 point, as published. The gauntlet **champion**.
- `design/argus7_v2.yaml` — produced by the optimiser. The gauntlet **challenger**.

## 6. Layer specifications

**6.1 Aero.** XFOIL sweeps for FX 63-137, S1223, E387, SD7037 across Re 0.3–1.5 M, α −6…+18°, producing a polar database. NeuralFoil provides the GPU-resident surrogate for the optimiser inner loop, validated against the XFOIL database. AVL (built from source) supplies neutral point, static margin, span efficiency `e`, and control derivatives from a model generated out of the YAML. A component drag buildup (wetted areas, form factors, interference) gives C_D0. SU2 RANS on the STEP solid, meshed by gmsh, supplies an independent C_D0 at selected points.

**CFD feedback mechanism:** RANS never runs in the loop. Instead it produces a scalar correction `k_cfd = C_D0_RANS / C_D0_buildup` at each validated point. If `k_cfd` is consistent across points (spread < 10%), its mean is applied as a fixed multiplier to the buildup inside the optimiser, and the optimiser is re-run. If the spread exceeds 10%, the buildup is treated as unreliable, no correction is applied, and the discrepancy is reported as an open risk rather than silently averaged away.

**6.2 Propulsion.** BEMT propeller design plus an off-design efficiency map η(J, RPM, ρ). Engine model: power vs RPM vs altitude with a BSFC map anchored on the report's 270 g/kWh assumption and its ≤250 target, belt reduction, alternator load for the 500 W payload.

**6.3 Structures.** Analytic spar cap sizing (tension 800 MPa, compression 600 MPa allowables per report §5), then CalculiX FE on the wing box for the +5.7 g ultimate case, compression-cap buckling, and gust cases. Feeds a **physics-based wing mass model** back into the optimiser — wing mass must not be a fixed constant while AR is free.

**6.4 Mission sim.** Batched torch. ISA atmosphere, drag polar, BSFC map, fuel-burn integration with altitude scheduling and continuous payload electrical load. Fully differentiable. Runs on CUDA.

## 7. Optimisation problem

**Objective:** maximise loiter endurance (days) at 50 kg / 500 W payload. Secondary objective for the Pareto pass: self-deploy range.

**Design vector:**

| Variable | Range |
|---|---|
| Wing area S | 2.5 – 6.0 m² |
| Aspect ratio AR | 14 – 30 |
| Taper λ | 0.30 – 0.70 |
| Washout twist | 0 – 5° |
| MTOW | 180 – 320 kg |
| Loiter altitude | 2,500 – 5,000 m |
| Prop diameter | 0.6 – 1.0 m |
| Reduction ratio | 1.5 – 3.5 |
| Engine power class | continuous scaling, discretised to real candidates post-hoc |
| Airfoil | categorical — optimiser run once per candidate, compared |

**Constraints:**

| Constraint | Bound |
|---|---|
| Stall margin | V_loiter ≥ 1.15 · V_stall |
| Climb margin | P_avail / P_req ≥ 1.3 at SL, MTOW |
| Static margin | 8% ≤ SM ≤ 20% MAC |
| Mass closure | Σ components = MTOW exactly |
| Fuel volume | fuel must fit wing tank volume from t/c and planform |
| Prop tip Mach | ≤ 0.75 |
| Span | ≤ 12 m (packaging/transport) |
| Gust load | n_total ≤ 3.8 limit |
| Regulatory band | **soft** — see §11 assumption A1 |

**Method:** Stage 1 Sobol DOE of 2²⁰–2²³ points batched on GPU with feasibility filtering; Stage 2 autograd gradient refinement (Adam then L-BFGS) on top-K feasible seeds using an augmented-Lagrangian treatment of constraints; Stage 3 CMA-ES for local-minimum escape and NSGA-II for the endurance/range/complexity Pareto front.

## 7b. Materials & manufacturability (amendment, added 2026-08-20 at sponsor request)

Materials and build method were absent from the original spec. They are not a
downstream detail: the wing mass model and the achievable C_D0 both depend on
them, and both feed the endurance objective directly.

**Grounding:** `research/materials_pack.md` (31 sources).

**Load-bearing results the optimiser and structures layer must consume:**

| Result | Value | Consequence |
|---|---|---|
| Mass-to-endurance exchange rate | **1.5 h/kg** | The scoring currency for every material decision |
| Laminar surface tolerance at Re 0.6–1.1 M | h/λ 0.031–0.044 single-wave | ~6× looser than the sailplane rule of thumb; allowable waviness scales Re^−0.75 |
| Measured moldless homebuilt wings (NASA TP-2256) | h/λ 0.0030–0.0046 | Pass with 2.6–4.9× margin — a garage build **can** hold laminar flow |
| Film-wing endurance penalty | 16.6–23.3 h | Drag −5.7…−12.4 h, measured ΔC_Lmax −0.2 → −3.8 h, +4.9 kg → −7.3 h |
| Wing is stiffness-critical, not strength-critical | 14.2% semi-span tip deflection at limit | Figure of merit is **E/ρ**, not ultimate strength |
| Wing gross internal volume | **143 L** | Against ~120 L fuel required; realistic tankage ~50 L — see §11 A4 |

**Recommended assignment** (28.9 kg wing, closes with 3.6 kg spare): pultruded UD
carbon spar caps; COTS roll-wrapped tube booms; printed ribs, wingtips, fittings
and mounts; moulded skin. Rejected: round-tube wing spar (costs exactly 2.07× a
cap-and-web spar — the ratio is `2h/D`, pure geometry); printed skins (+18.7 kg,
fails closure); film skin (cannot form the leading edge, and its scalloping is a
*spanwise* disturbance for which no criteria exist).

**Optimiser impact:** a buildability constraint is added to §7 — the design must
map to a material assignment that closes mass, and the wing mass model must be
driven by the chosen assignment rather than the report's 8.6 kg/m² sailplane
calibration. The premortem's top failure modes were budget and solo-builder
bandwidth, not aerodynamics, so build effort is a first-class criterion.

**Correction propagated:** the pack's §2.5 originally computed gross wing volume
with a hardcoded aerofoil shape factor of 0.68 — a NACA-4-digit value. Measured
FX 63-137 is 0.6062 (shoelace integration), a +12.2% bias. This is the same
constant ruling P14 caught in the Task 3 area test, recurring independently in
prose. 143 L supersedes 160 L.

## 8. Validation gates

No layer is used downstream until it passes an external check.

| Layer | Gate | Threshold |
|---|---|---|
| XFOIL | vs measured FX 63-137 (Stuttgart Profilkatalog / UIUC LSATs) | C_l/C_d within 10% in the drag bucket |
| NeuralFoil | vs the XFOIL database | within 5% |
| AVL | vs analytic lifting-line, elliptical wing | `e` within 2% |
| Mission sim | vs closed-form Breguet on the same polar | **< 0.1%** |
| **Whole model** | **fed Vanilla VA001 parameters, reproduce its measured 8-day FAI record** | **within 10%** |
| CFD | vs XFOIL + buildup, three-way | C_D0 within 15% |
| FEA | vs analytic beam theory | root bending within 5% |

The VA001 gate is the strongest available: a real aircraft with a real record. A model that cannot reproduce it is not trusted regardless of internal consistency.

## 9. Adapted gauntlet protocol

`skill-gauntlet` is built for skill/prompt A/B testing; `plan.md` correctly flagged it N/A for engineering. Its *method* transfers:

- **Champion:** v1.0 design (250 kg, AR 22, S 3.9). **Challenger:** optimised v2.0.
- **Pre-registered conjunctive adoption gates,** fixed before results are seen: challenger adopted only if endurance improves ≥5% **AND** no regression on static margin validity, climb margin, structural feasibility, fuel volume feasibility, buildability proxy, or regulatory band.
- **Blind judge panel:** judge subagents score both designs with identity stripped and order randomised (labelled A/B).
- **Planted-flaw key:** a seeded copy carrying K deliberate errors is scored alongside. Judges catching < 80% of planted flaws are declared uncalibrated and the panel is re-run. This verifies the judges before their verdict is trusted.
- **Cross-check auditor:** independent re-derivation of the challenger's headline numbers.

**"Buildability proxy" is defined concretely** (it gates adoption, so it cannot be left to judgement): a weighted score over — span ≤ 12 m single-piece or ≤ 3 sections; AR ≤ 25 (above this, spar tooling and jig cost rise sharply for a solo builder); engine matched to a real purchasable unit from report §6's shortlist rather than an interpolated power class; no more than one bespoke subsystem beyond those already in v1.0; and parts count within 1.25× of v1.0.

Followed by `premortem-evolved` on the resulting build plan.

## 11. Assumptions requiring confirmation

- **A1 — Regulatory constraint is soft.** The optimiser may cross 250 kg; every result is tagged with its regulatory band, and both the best unconstrained point and the best ≤250 kg point are reported. *(Asked; not answered before "go". Flipping to hard is a one-line change.)*
- **A2 — Mission requirements fixed.** Payload 50 kg / 500 W continuous and the loiter mission are inputs, not optimisation variables.
- **A3 — v1.0 is the champion as published**, including its own stated caveats, without retroactive correction.
- **A4 — the wing cannot hold its specified fuel, and this is unresolved.** Gross
  wing internal volume is 143 L; realistic tankage (50% chord between spars, 80%
  of span, 88% net of structure) gives ~50 L, against the ~120 L the report
  requires. Report §2 places fuel at the aerodynamic centre specifically to hold
  CG travel under 0.5% MAC as fuel burns, so relocating 101.5 kg — 40.6% of MTOW —
  into the fuselage is a stability problem, not a packaging one. **Escalated to the
  sponsor; it changes the aircraft, not the code.** The optimiser's existing fuel-volume
  constraint (§7) will simply refuse any design that cannot carry its own fuel, so
  freeing the design point may resolve it by moving to a larger or thicker wing.

## 12. Risks

| Risk | Mitigation |
|---|---|
| OCP/build123d wheels immature on Python 3.14 | Dedicated 3.12 venv fallback, already confirmed available and scripted in `setup_env.sh` |
| SU2 release URL drift / build failure | Failure-isolated install; OpenFOAM via upstream repo as fallback; CFD is a validator, not a blocker |
| AVL Fortran build needs X11 plotlib | Build with `Makefile.gfortran`, headless via xvfb; AeroSandbox VLM as fallback |
| CFD wall time (hours–days on 32 cores) | Restricted to 3–6 validation points, never in the loop |
| Optimiser converges to an unbuildable point (e.g. AR 30) | Buildability proxy in adoption gates; span and structural constraints active; Pareto front reported, not just the optimum |
| Physics-based wing mass model miscalibrated as AR moves | Calibrated against the design pack's measured 8.6 kg/m² and ASW 27B's 12.9 kg/m² |

## 12b. Implementation phasing

This spec is deliberately larger than one implementation plan. The plan derived from it decomposes into five phases, each independently verifiable and each ending in a committed, tested artifact:

| Phase | Content | Exit criterion |
|---|---|---|
| P1 | Data contract + geometry closure + CAD rebuild | STEP/STL/SCAD regenerate from YAML; closure tests pass; three-view renders correct |
| P2 | Aero stack (XFOIL, NeuralFoil, AVL, buildup) | §8 gates 1–3 pass |
| P3 | Mission sim + VA001 benchmark reproduction | §8 Breguet and VA001 gates pass |
| P4 | Prop, structures, CFD validation | §8 gates 6–7 pass; `k_cfd` determined |
| P5 | Optimisation, gauntlet, premortem, report v2.0 | Adoption gates evaluated; report regenerated |

Phases P2–P4 are mutually independent once P1 lands, and are the natural fan-out points for parallel subagents.

## 13. Deliverables

1. Corrected parametric CAD — STEP, STL, regenerated OpenSCAD, three-view + isometric renders.
2. Installed, validated simulation stack with all gates in §8 passing and recorded.
3. Optimised design point plus Pareto front, with the v1.0-vs-v2.0 comparison.
4. Gauntlet results including planted-flaw calibration evidence.
5. Premortem on the revised build plan.
6. Report v2.0 with a full changelog against v1.0.
